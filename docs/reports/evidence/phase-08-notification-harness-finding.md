# Phase 08 notification instrumentation completion finding

The first A35 run exposed a test-harness completion race. Its actual System UI ACK and cached action-node replay reported UI `PASS`, but the independent SQLite assertion correctly failed: reminder/job `ACKNOWLEDGED`, task `TODO`, **one** local alarm-registration row remained. Preserve this failed cohort: [initial JSON](phase-08-emulator-expansion/ex20261028/20261028T033555858446Z-79131ca4-notification.json), [initial log](phase-08-emulator-expansion/ex20261028/20261028T033555858446Z-79131ca4-notification.log).

The best-supported diagnosis is that finishing instrumentation stopped the target process after its `goAsync` receiver saved ACK but before its worker finished cancellation/reconciliation. This is an inference from the partial state, worker/lock structure and successful bounded retry, not a captured trace proving the exact interruption point. AOSP's `finishInstrumentationLocked` calls `forceStopPackageLocked` when `!instr.mNoRestart` (lines 13881–13883 in the source retrieved on 2026-10-28). [AOSP primary source](https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/master/services/core/java/com/android/server/am/ActivityManagerService.java). This citation follows mutable `master`; no unverified commit or exact emulator-binary match is claimed.

The harness now completes a private provider `capabilities` call before exiting. That existing endpoint takes the same remote store lock, reads delivery settings and builds capability JSON. It does **not** call `reconcile`, change the saved action, or repair registration SQL. Capability inspection may ensure Android's notification channel exists; it is not wholly free of platform effects. The barrier waits for the receiver worker to release its store lock, allowing the already implemented production action/reconciliation path to finish before instrumentation teardown.

The A35 retry again used the actual notification shade, clicked the exact owned ACK action and replayed the cached node. It then recorded `read_only_remote_store_barrier_completed`; independent SQL showed reminder/job `ACKNOWLEDGED`, task `TODO`, and **zero** registrations. [Retry JSON](phase-08-emulator-expansion/ex20261028/20261028T080611353825Z-c61918e1-notification.json), [retry log](phase-08-emulator-expansion/ex20261028/20261028T080611353825Z-c61918e1-notification.log). UI completion alone remains insufficient evidence of durable completion.

Production reconciliation already handles stale derived registration rows after process death: the durable action remains authoritative, while retained registration metadata lets a later startup/reconciliation cancel and remove stale platform work. This finding required a harness barrier, not a production reconciliation rewrite.

A separate early cleanup issue came from the notification shade intercepting later app UI actions. The CLI now runs `cmd statusbar collapse` before each instrumentation UI driver. That is harness surface preparation; it neither acknowledges a reminder nor edits storage. Earlier failed evidence remains preserved.

These results concern the tested emulator and synthetic fixtures. Physical-phone notification delivery, OEM behavior and real speech/audibility remain pending.
