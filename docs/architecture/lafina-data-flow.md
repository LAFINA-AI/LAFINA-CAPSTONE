# LAFINA data flow diagram: implementation evidence

The [Level 1 DFD](lafina-data-flow-diagram.svg), embedded as a [PNG](lafina-data-flow-diagram.png) in the [README](../../README.md#data-flow-diagram), decomposes the context diagram's Process 0. It describes the principal student workflows in this checkout as inspected on **2026-11-20**. It is a logical feature model, not an exhaustive database schema, endpoint inventory, execution sequence, or production availability test.

## Boundary and notation

- **Inside LAFINA:** the Android client, its local application/native services, the owner-confirmed Electron client, and the shared backend. Authentication, sync and online feature processes therefore include their backend work; the backend is not an external entity.
- **External entities:** E1 Student, E2 DeepSeek, E3 Pinecone, E4 ElevenLabs. These are the same entities used in the [context diagram](lafina-context-diagram.svg). University files enter through the student; no university portal integration is implied.
- **Numbered rectangles:** processes that transform input data into output data. White boxes marked as process aliases repeat an existing process. For example, the 2.0 alias beside 4.0 shows confirmed assistant changes entering the same persistence logic used for manual planning.
- **Open-ended D symbols:** logical data-store views. Repeated IDs are the same store. These groups are not disjoint physical tables: profile fields in D2 use the user/preference records also represented in D1, and COR metadata in D6 uses local settings. They do not create extra databases or duplicate copies of those records.
- **Arrows:** named data moving in the indicated direction. User choices are represented as input data, not control-flow branches. The E2/E3/E4 flows distinguish request data from returned content.

The diagram uses the README's established product boundary. Only the Android implementation and available backend integration/reference source were inspected. The Electron feature set is owner-confirmed in the README; its packaging, persistence adapters, and native behavior were not inspected. Android-specific engine and database names must not be read as verified Electron internals.

## Data-store mapping

| ID | Logical data | Physical backing / scope |
| --- | --- | --- |
| **D1** | Identity, session references, preferences and local settings. | Android `lafina.db`: `users`, `active_session`, `user_preferences`, `local_settings`, with platform credential storage handled by the cloud/session client. Not every setting is synchronized. |
| **D2** | Seven core personal record types and their synchronization state. | SQLite profile payloads, `tasks`, `events`, `time_blocks`, `reminders`, `notes`, `custom_categories`; `sync_outbox`, `sync_metadata`, `sync_state`, `sync_control`, `sync_conflicts`. Profile payloads are assembled from user/preferences records; there is no separate local `profile` table. |
| **D3** | Chat history and optional personal memory. | SQLite `chat_sessions`, `messages`, `chat_memories` and associated settings. For signed-in accounts with "Sync chat history" on, sessions and messages sync as `chat_session` / `chat_message` through the same outbox and `/v1/sync/batch`, declared only to a server that lists them (ADR-040). At most 20 chats per account, on the phone and the server; nothing is deleted to make room. Attachment files, memory notices, memories, Temporary Chat and guest chats stay on the phone. |
| **D4** | Local handbook pack, searchable chunks and citations. | Bundled/device handbook pack, populated SQLite `handbook_meta`, `handbook_chunks` and `handbook_chunks_fts` (FTS5). Retrieval depends on usable local data and supported search. Pack provisioning/seed ingestion is outside this feature DFD. |
| **D5** | Device alarm clocks, reminder delivery state and behavior history. | SQLite `alarms`, `reminder_delivery_jobs`, `reminder_delivery_events`, `reminder_delivery_styles` and relevant behavior records; native alarm scheduling state. The reminder entity itself is in D2; the alarm-clock entity is device-local. |
| **D6** | Local files, recording/import metadata and generated outputs. | SQLite `recorded_meetings`; COR review/ledger and academic metadata in local settings; calendar import batch JSON; app-private audio/files and generated/exported artifacts. Raw recording chunks are deleted after transcription unless retained via `keepAudio`; export/share destinations can differ from app-private storage. |
| **D7** | Backend account/access state, synchronized personal data, voice session and AI usage records. | Cloud PostgreSQL (Neon in the documented deployment), accessed through the backend. No direct mobile SQLite-to-Neon or client-to-provider credential path is implied. |

Local schema references: [database initialization](../../src/storage/dbInit.ts), [alarm schema](../../src/storage/alarmSchema.ts), [delivery schema](../../src/storage/deliverySchema.ts), [chat memory schema](../../src/storage/chatMemorySchema.ts), [handbook schema](../../src/storage/handbookSchema.ts), and the stores linked above. D1–D6 are logical views over local data/resources; they do not imply six separate SQLite databases.

## Backend evidence and limits

Backend responsibilities were cross-checked against the available read-only local reference under `.local/call-lafina-backend/app/`: `database.py`, `api/v1/auth.py`, `api/v1/sync.py`, `api/v1/ai.py`, `api/v1/voice.py`, `api/v1/meeting_notes.py`, and `clients/pinecone_index.py`. These are reference snapshots, not proof of the currently deployed revision. The maintained repository is [LAFINA-backend](https://github.com/LAFINA-AI/LAFINA-backend); the mobile integration/deployment history is in [backend_integration/README.md](../../backend_integration/README.md).

The diagram does not claim a successful signed-in provider request, device alarm delivery, microphone permission test, audio playback, cross-device sync test, or Electron validation. Service availability remains dependent on deployment, account authorization, configuration, connectivity and the applicable online-mode choice. Core manual planning does not require successful speech, cloud AI or model execution.
